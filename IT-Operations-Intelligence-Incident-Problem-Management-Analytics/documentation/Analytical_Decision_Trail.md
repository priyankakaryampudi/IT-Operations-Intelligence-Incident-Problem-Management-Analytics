# Analytical Decision Trail

Every material choice in the project, in order, with the alternatives considered and the reason for the choice. Each decision states its consequence so a reviewer can see what it cost.

**Origin.** The project starts from an internship observation at Protiviti: incidents resolved one at a time, with no record or feedback loop, so a recurring issue could not be told apart from a new one. D-01 below is the first decision made once that observation became a project — to test it on real, public data rather than internship or client data.

| ID | Decision | Alternatives considered | Why | Consequence |
|----|----------|------------------------|-----|-------------|
| D-01 | Use a real, anonymised ServiceNow incident log. | Synthetic data. | Findings are credible only if the mess is real: multi-row incidents, placeholders, odd dates. | Cleaning became part of the deliverable (see Data Quality Log). |
| D-02 | Frame the work as a loop: Detect, Prioritise, Investigate, Decide, Act, Monitor. Limit depth to two patterns. | A one-off incident report; a full prioritised backlog with owner mapping for every pattern; stakeholder analysis and formal acceptance criteria. | A report ends at findings. The loop ends at a decision and a metric. There are no real stakeholders in a public dataset, so stakeholder sections would be filler. | Scope stays deliverable. Depth is applied to the top patterns only. |
| D-03 | Pick each incident's final row by **latest update time**. | Keep the row where state = `Closed`. | `Resolved` and `Closed` are both terminal, and `-100` exists. Filtering on `Closed` drops valid incidents. | Robust to state quirks, but exposed to DQ-08 (text ordering). |
| D-04 | Break ties with `sys_mod_count DESC`. | Arbitrary `LIMIT 1`; keep both tied rows. | The higher modification count is logically the later state. Reconciles to 20,769. | Removes 1,367 duplicate rows. |
| D-05 | Parse dates **inside each query** with `STR_TO_DATE`. | Convert the columns permanently. | Keeps the raw table untouched and every step reproducible from the CSV. | Longer queries, one consistent format string. |
| D-06 | Read results with minimum sample sizes: groups n >= 100, categories n >= 40; never treat `?` as real. | Rank on raw percentages. | A 50% breach rate on 6 incidents is 3 tickets: noise. | Small groups and placeholders are excluded from conclusions. |
| D-07 | Redefine recurrence as **same caller + same category**. | Same asset + category (the original idea). | `cmdb_ci` is `?` on 99.75% of incidents. Testing the field before trusting it exposed the problem. | Recurrence measures repeat *reporting*, not repeat *asset failure*. Stated as a limitation. |
| D-08 | Primary window **14 days**. Test 7 and 30 days as sensitivity. | A single arbitrary threshold. | 7 days may miss genuine repeats that resurface slowly. 30 days risks catching unrelated incidents that share a category. 14 days is a common operational cycle. | Sensitivity results are produced by `sql/06` and `python/recurrence_validation.py` (results log at the top of `sql/06`). |
| D-09 | Summarise recurrence by caller + category (3 or more incidents), do not list pairs. | Print all 73,339 pairs. | Pair lists are dominated by a few callers and are unreadable. | A ranked list that feeds candidate selection directly. |
| D-10 | Keep `Caller 1904` and `Caller 290` in the data; flag them. | Delete them as outliers. | Deleting hides the most concentrated pattern. Their span (about two months) is sustained, not a one-day burst. | Labelled "possible automated source, needs validation". Robustness run excluding them is provided. |
| D-11 | Investigate two patterns in depth: Category 46 (cross-caller, cleanest story) and Caller 1904 / Category 51 (most concentrated). | Investigate all top-20 combinations. | Depth beats breadth for a portfolio case. The two patterns lead to different interventions. | `Caller 290 / Category 28` (212 incidents) and `Caller 4514` combinations are logged as next candidates, not investigated. |
| D-12 | Write findings as fact, pattern, contributing factor, **hypothesis**, what to validate. | Claim a proven root cause. | The data shows association, not cause. Reopen rates near zero cannot prove a routing cause. | Recommendations are labelled as hypotheses. |
| D-13 | Classify each intervention: technical fix, routing/ownership, knowledge gap, change-control weakness, automation opportunity. | Free-text recommendations. | A fixed taxonomy makes patterns comparable and assigns an owner type. | Category 46 = routing/ownership. Caller 1904 / Category 51 = automation opportunity. |
| D-14 | Define KPIs with baselines before recommending. | Recommend without measures. | A recommendation without a metric cannot be tested. | Category 46 reassignments 0.92, breach 54.1% (on `incidents_final_v2`, superseding the original 0.83 / 25.9%). Caller 1904 / Category 51 volume 399 (unchanged). |
| D-15 | Re-implement the recurrence rule in Python. | Trust the SQL alone. | Two independent implementations of the same definition expose logic errors. | `python/recurrence_validation.py` reconciles to the SQL pair count: 73,339 at 14 days in `text` mode (v1), 73,359 in `parsed` mode (v2). |
| D-16 | Dashboard: three pages, minimal, teal and gold, Verdana throughout. | Default multicolour Power BI theme; one dense page. | Consistent visual language across dashboard, brief and case study. Highlights reserved for findings. | Overview, recurrence intelligence, action board. |
| D-17 | Provide `incidents_final_v2`, then run 03-06 on it and publish the corrected figures — rather than silently changing the model late, or leaving the issue unresolved. | Silently change the model late; ignore the issue; leave DQ-08 open forever with a caveat. | Changing the model after figures were derived without running the queries again would make repo and results inconsistent. Hiding the issue would be worse, but so would never closing it. | DQ-08 and DQ-11 are now **Resolved**: `incidents_final_v2` is the published model. See D-19 for the reconciled numbers. |
| D-18 | Define the incident-level flag once, on calendar days and a strictly earlier timestamp, and use it in both SQL (`06 / V2`) and Python. | Exact elapsed time in Python. | A test pair 14.92 days apart was flagged by SQL (`DATEDIFF` = 14) but not by Python, so the two could never reconcile. Found by testing a boundary case. | V1, V2 and V3 agree between SQL-equivalent queries and Python on synthetic data, including ties and non-chronological incident numbers. Now also run on the real file (D-19) — matched. |
| D-19 | Run `sql/03` to `sql/06` on `incidents_final_v2` against the real file, 24 Sep 2026, and republish every headline figure. | Publish v2 alongside v1 indefinitely and let the reader reconcile them. | A finished deliverable should have one current set of numbers, not two, with the superseded ones clearly marked for transparency. | Overall SLA breach 16.9%→39.4%; backlog 38.6%→0.0% (1 incident); Category 46 breach 25.9%→54.1%; Group 70 breach 8.4%→18.6%. Recurrence barely moved (73,339→73,359 pairs at 14 days) — the bug affected row-selection-dependent fields (`active`, `made_sla`), not `opened_at`-based recurrence. Full table in `README.md`, "Data quality, resolved". |
| D-20 | Run the Category 46 reassignment comparator (`sql/05` C7a/C7b) and the repeat-reporting share (C8) before finalising the write-up, rather than publishing 0.92 as self-evidently "high". | Publish 0.92 next to the original 0.83 baseline and let the reader infer it's elevated. | 0.92 looks high only against Category 46's own superseded number. Without a dataset-wide comparator, that's not evidence — it's an artefact of which baseline you show. | 0.92 is close to the dataset-wide average (0.99) and ranks 18th of 26 categories: not a differentiator. Reframed the pattern around the breach rate (54.1% vs 39.4%) instead. C8: 54.1% of Category 46 (1,079/1,993) is repeat reporting by 203 callers — well above the original 8% lower bound. |
