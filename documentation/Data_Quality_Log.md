# Data Quality Log

Every data problem found during the project, how it was detected, what it affected, and what was done. Status: **Resolved** (fixed in the model), **Mitigated** (handled in analysis, cannot be fixed at source).

| ID | Issue | Detection | Impact | Treatment | Status |
|----|-------|-----------|--------|-----------|--------|
| DQ-01 | **File is an event log, not an incident table.** 119,998 rows for 20,769 incidents (about 5.8 rows each; one incident has 58). | `COUNT(*)` vs `COUNT(DISTINCT number)` (01 / P1, P2). | Every count on the raw table would measure how often incidents were *touched*, inflating volume for busy incidents. | Collapse to one row per incident (`incidents_final`). All analysis runs on the view. | Resolved |
| DQ-02 | **Ties on the final-row rule.** First version returned 22,136 rows instead of 20,769. | Reconciliation of view count to distinct incidents (02). | 1,367 extra rows would have double-counted incidents. | Added `sys_mod_count DESC` as a tie-breaker. Count reconciles exactly. | Resolved |
| DQ-03 | **Two terminal states plus an artefact state.** `Resolved` and `Closed` both mean finished; `-100` is unknown. | `SELECT DISTINCT incident_state` (01 / P5). | Filtering on `Closed` would drop incidents that only reached `Resolved`. | Final row chosen by time, not by state. | Resolved |
| DQ-04 | **Dates stored as day-first text.** Values such as `29/2/2016 11:29`. | First resolution-time query returned NULL for every row; sample of `resolved_at` (01 / P6). | Date maths and ordering silently failed. | Parse with `STR_TO_DATE(col, '%d/%m/%Y %H:%i')` inside each query. Raw columns left untouched. | Resolved |
| DQ-05 | **`?` placeholder for missing values.** `cmdb_ci` 20,717 of 20,769; `assignment_group` 2,157 (was 2,205 pre-DQ-08); `category` 7 (was 10). One Category 36 incident has no `resolved_at`. | Placeholder audit (01 / P7), baseline queries (03). | Placeholders form fake groups (the `?` group shows 51.4% breach, 1,108 of 2,157, corrected model). | Excluded from category and group conclusions. The 2,157 unassigned incidents are reported as an ownership-recording gap. | Mitigated |
| DQ-06 | **Asset field unusable for recurrence.** Only 52 incidents carry a real `cmdb_ci` (max 3 per asset). | Coverage check (04 / R1). The asset-based self-join returned only `?` matches (R2). | "Same asset broke twice" cannot be measured. | Recurrence redefined as same caller + same category (04 / R3-R5). Stated as a limitation. | Mitigated |
| DQ-07 | **MIN/MAX on text dates.** `first_seen` `10/5/2016` came out *after* `last_seen` `9/5/2016`. | Sanity check on the two extreme callers (04 / R6). | Wrong time spans, wrong interpretation of whether a caller was a burst or sustained. | Parse before aggregating. Corrected spans: about two months each. | Resolved |
| DQ-08 | **Final-row ordering uses text.** `ORDER BY sys_updated_at` on a `D/M/YYYY` text column sorts alphabetically (`29/2/2016` sorts after `2/3/2016`), so the chosen row may not be the true latest. | Found while documenting DQ-07: the same bug class applies to the view. | Changed the selected row for **8,018 of 20,769 incidents (38.6%)**. SLA breach moved 16.9% → 39.4%; backlog moved 38.6% → 0.0%; Category 46 breach moved 25.9% → 54.1%. Recurrence was not materially affected (73,339 → 73,359 pairs at 14 days). | `incidents_final_v2` (parsed ordering) built and reconciled in `sql/02`. **03-06 run on v2; all figures in README, case study, appendix and dashboard now use v2.** v1 is kept only for the before/after comparison. | **Resolved** |
| DQ-09 | **Pair explosion.** 73,339 caller + category pairs at 14 days (v1); 73,359 on v2. One caller with hundreds of incidents produces combinatorially many pairs. | Count query (04 / R4). | The pair list is unreadable and dominated by a few callers. | Summarise by caller + category (3 or more incidents) and report counts instead of pairs. | Mitigated |
| DQ-10 | **Extreme callers.** `Caller 1904` 437 incidents and `Caller 290` 239, each spanning about two months. | Top-caller counts and corrected time span (04 / R3, R6). | Unlikely to be single people. May be service accounts or automated sources. | Not removed. Flagged as a candidate and labelled "needs validation". Sensitivity run without them (06 / V3): on v2 the 14-day pairs fall from 73,359 to 9,647 (about 87%), while flagged incidents fall only from 25.2% to about 22.8%; the pair count is dominated by these two callers, the repeat rate is not. | Mitigated |
| DQ-11 | **Backlog reflected the DQ-08 bug, not a real backlog.** 8,019 incidents (38.6%) showed `active = true` on v1. | Backlog query (03 / B6). | Overstated the operational backlog substantially. | Checked on `incidents_final_v2`: **1 record (0.0%) still shows `active = true`**, state "New": INC0029233, opened 13 May 2016. Its record carries resolved and closed timestamps (17 and 22 May 2016), so it is most likely a row-selection quirk, not a genuinely open ticket. Its event rows have not been inspected individually. The published 38.6% backlog was itself a DQ-08 artifact — resolved together with DQ-08. | **Resolved** |
| DQ-12 | **Dataset size differs from the published description.** The loaded file has 119,998 event rows and 20,769 incidents; the public description of the source dataset quotes 141,712 events across 24,918 incidents. | Compared load counts to source documentation. | Early planning notes quoted the published figures. | **All figures in this repository refer to the file actually loaded** (119,998 rows, 20,769 incidents). The loaded file's `opened_at` spans 29 Feb to 13 May 2016. That does not prove it is a subset of the public file. | Documented discrepancy, cause not confirmed |
| DQ-13 | **Caller `?` treated as a real caller.** Three incidents have `caller_id = '?'`, and the recurrence joins match them to each other. | Found while reconciling v1 pair counts (73,338 vs 73,339). | Accounts for the 1-pair gap on v1. Negligible on v2 totals. | Noted, not removed; the published pair counts include them. | Mitigated |
